# 審查變更

Review 預設唯讀。使用者明確要求修改時，才動檔案。

## 步驟

1. **確定審查範圍。** 確認目標（diff 範圍、分支、PR、commit），以及相關的規格、驗收條件或 issue。讀完整的 diff，以及被修改程式碼周圍、會影響判斷的部分。
2. **先建立預期。** 從規格、公開契約、不變量和既有行為，寫下這次變更「應該」做到什麼；不要只從實作本身推斷它是否正確。
3. **對抗式檢查。** 依變更的性質，挑相關的面向逐一檢查：
   - 正確性：邊界輸入、錯誤路徑、無效狀態、並行、資源釋放。
   - 安全性：輸入驗證、授權檢查、敏感資料、注入。
   - 相容性：公開 API、持久資料、設定格式、版本行為、migration。
   - 回歸：既有呼叫端和使用情境是否仍然正常。
   - 測試：新的行為有沒有測試保護、測試是否真的會在出錯時失敗。
4. **為每個 finding 取得證據。** 每一條都要有精確位置（`file:line`）、具體的失敗情境（什麼輸入或狀態會導致什麼錯誤結果），以及可重現或可直接檢查的證據。能跑的檢查就跑，例如測試、typecheck，或一段簡短的重現程式。
5. **篩掉沒有根據的項目。** 拿不出失敗情境的推測不列為 finding；真的有疑慮時，標為「待確認」並說明缺少什麼證據。不要為了湊數而製造 finding，「沒有發現問題」是可以接受的結論。
6. **排序並回報。** 依嚴重程度排序，先列會造成錯誤結果、資料遺失或安全問題的項目，風格和可讀性建議放最後或省略。

## 回報格式

每個 finding：

- 位置：`file:line`
- 問題：一句話描述缺陷
- 失敗情境：具體的輸入或狀態 → 錯誤的結果
- 證據：執行過的檢查或可直接檢查的程式碼

最後附上：審查範圍、執行過和沒有執行的檢查、沒有涵蓋到的風險。
