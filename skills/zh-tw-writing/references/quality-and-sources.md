# AI 文案與台灣繁體中文 Don't / Do 寫作規範

> 版本：2026-11-17（增補：英文術語保留原則） · 語系：zh-TW · 範圍：ChatGPT / OpenAI、Claude / Anthropic、Gemini / Google、Grok / xAI、DeepSeek、Qwen、Llama、Mistral、Kimi、GLM 等大語言模型輸出的社群文案、行銷文案、文件、對話與工程報告。

## 定位、分級與判斷原則

這是**跨模型編輯規範**，不是 AI 來源偵測器，也不是能窮盡所有模型和語料的頻率統計。中文例句是依據社群觀察與編輯原則撰寫的示範改寫，**並非逐一對每家模型執行統計後的原始輸出**。模型版本、提示詞、題材與語言會改變輸出風格；不能把英文研究的比例直接套用到台灣繁體中文。

- **[L] 在地化／語意問題**：不符合台灣日常或技術慣例，或翻譯導致誤解。通常應改；但先檢查上下文。
- **[S] 風格密度問題**：語法本身正確，但公式化、堆疊或沒有資訊。應依文體修正，**不可當絕對禁詞**。
- **[F] 事實／信任問題**：虛構來源、數據、親身經歷、驗證或執行狀態。必須查證或明示未知，不得只做文字潤飾。

**保護不修改的範圍**：法規與機關正式名稱、直接引述、產品和 UI 原文、程式識別字、API、CLI、路徑、程式碼、錯誤訊息、數值、日期、網址、作者已表明的立場，以及台灣專業社群習慣直接使用的英文術語。修改術語時要保留原始意義，不能只做字串替換。使用者明確要求另一語系或特定品牌術語時，以該需求為準。


## G. 內容完整性、可信度與 Agent 回報（[F]，嚴格要求）

| # | Don't | Do |
|---:|---|---|
| G01 | 「根據研究顯示」卻沒有研究名稱 | 標明作者／研究／年份／連結，無來源就不冒稱研究。 |
| G02 | 「專家普遍認為」卻沒有具體專家 | 指出來源與範圍，或改為尚未驗證的主張。 |
| G03 | 自造「效率提升 73%」等假精確數字 | 保留實測值與條件；沒量測就不要給精確百分比。 |
| G04 | 虛構個人經歷：「我曾經遇過……」 | 只有使用者或來源提供真實經歷才寫。 |
| G05 | 虛構已完成的操作：「已部署」「已測試」 | 有工具紀錄與驗證結果才宣稱完成。 |
| G06 | 把推測說成已確定：「這代表……」 | 標示觀察、推論、尚未確認。 |
| G07 | 「兩種選擇各有優缺點」卻不做判斷 | 依需求、證據、風險提出條件式建議。 |
| G08 | 無視真正的取捨：「兼顧性能、成本、品質」 | 說明哪個目標優先、犧牲什麼。 |
| G09 | 「大部分人都……」無樣本或來源 | 說明研究對象或刪除概括。 |
| G10 | 「毫無風險／完全安全／100% 相容」 | 給出已驗證範圍與剩餘風險。 |
| G11 | 引用死連結、虛構 DOI、來源與主張無關 | 逐一驗證來源是否存在、是否真的支持主張。 |
| G12 | 借用工具／來源名稱增強權威 | 說清楚實際查過哪些東西與未查哪些。 |
| G13 | 把使用者尚未決定的方案寫成既定決策 | 明確區分「已接受」「建議」「待決定」。 |
| G14 | 把核准設計說成核准實作、推送或部署 | 區分決策與各種執行授權。 |
| G15 | 為了自然語氣改寫、刪掉法律限定詞或風險 | 保持原文立場強度、義務與例外條件。 |
| G16 | 問題沒答完就說「希望有幫助」 | 回覆實際答案、限制與下一步。 |
| G17 | 「我已完成全面研究」但只看一篇文章 | 列出實際查證範圍，避免過度宣稱。 |
| G18 | 模型因缺資料而自行補上姓名、價格、日期 | 用「未知／需確認」或提出待查問題。 |
| G19 | 「已保留所有原始資訊」卻未比較差異 | 透過 diff 或檢查項目逐項核對。 |
| G20 | 改寫時偷換讀者觀點或降低主張強度 | 保留原來的主張、否定程度和證據限制。 |

## H. 版面、標點與複製產物（[S]／[L]）

| # | Don't | Do |
|---:|---|---|
| H01 | 繁體中文正文大量半形逗號和句號 `, .` | 一般中文句子用 `，。`；程式碼與識別字例外。 |
| H02 | 中文文章全篇使用英文彎引號 `“ ”` | 一般引語使用「」；引中引用用『』。原文引述例外。 |
| H03 | 每個標題加入表情符號和驚嘆號 | 只有語氣或平台真的需要才加入。 |
| H04 | 每個清單項都加粗、每兩行一個分隔線 | 用少量有意義的視覺層級。 |
| H05 | 複製工具輸出的 `turn0search...`、引用佔位碼 | 移除無效標記；保留可檢查的正式來源。 |
| H06 | 複製工具提示中的 `[填入姓名]`、`{company}` 直接發送 | 補真實資訊，或明確標為未填欄位。 |
| H07 | 沒有檢查來源就保留網址上的追蹤參數 | 非必要追蹤參數可清除，但不得破壞 URL 功能。 |
| H08 | 簡轉繁後保留不自然異體字「爲、羣、綫」 | 依台灣語境採「為、群、線」。 |
| H09 | `干/乾/幹`、`后/後`、`发/發/髮` 直接逐字轉換 | 依詞義與上下文校正，不做錯誤一對一替換。 |
| H10 | 無必要的零寬字元、不換行空白 | 清除異常格式控制字元，但避免破壞程式碼和原文資料。 |
| H11 | 技術文保留大量行銷式形容詞 | 改用版本、條件、操作、錯誤處理與限制。 |
| H12 | 社群文硬套學術論文語氣 | 依平台與受眾使用自然的台灣中文，不必刻意加語助詞。 |

## I. 模型差異：哪些有跨模型證據，哪些沒有

- **研究證據（限定原研究語料）**：Graphite 2026-09-16 研究以 10,000 篇真人文章與 90,000 篇 AI 文章比較英文寫作特徵；研究列出的 GPT-6 Astra 偏向修正式／讓步式措辭（rather than、not simply），Claude Opus 5 偏向加強語氣、less X more Y，Gemini 3.1 Pro 常用 furthermore 或 is not just 等形式。不同版本會變化，這不是台灣繁體中文的直接頻率統計。
- **中文社群觀察**：「不是……而是……」、開場說「其實」、假性深度、段落整齊、破折號、粗體和空泛金句在社群討論中常被提及。這些是編輯警訊，不是辨識 AI 的可靠判準。
- **不能強行歸因**：沒有找到同一套、足夠大且可重現的台灣繁體中文比較，能有把握地把以上每個中文句型按 ChatGPT、Claude、Gemini、Grok、DeepSeek、Qwen、Llama、Mistral 等逐家排序。因此本清單統一做跨模型檢查，不附臆測的「某模型專屬」標籤。

## J. 可複用的跨模型寫作指令（簡化版）

```text
請以台灣繁體中文撰寫，依讀者、文體與原文意圖調整語氣。
先給具體結論，再補必要依據；避免空泛背景、罐頭開場和結尾。
不要機械重複「不是 X 而是 Y」「不只 X 更是 Y」「真正的關鍵」「本質上」「隨著時代」等句型；只有真的有語意功能才使用。
不要堆砌賦能、打造、無縫、全方位、解鎖、至關重要、深度探討等形容或商業套話，改說明具體動作與結果。
使用台灣慣用詞及技術術語；台灣專業社群常直接使用的英文（如 API、SDK、PR、commit、Token、Agent）優先保留原文，不要強制全譯。已有自然台灣譯名（如快取、資料庫、伺服器、微調）可用中文；依讀者和專案既有慣例決定。遇到多義詞先依上下文判斷，不做盲目字串替換。
避免多餘的「對……進行……」「扮演重要角色」「有能力去……」等翻譯腔。
有必要才使用標題、列表、表格、粗體、emoji、破折號；不要刻意把每段都寫成三項。
保留事實、數字、日期、專有名詞、法規、引用、程式碼、URL、原文立場與不確定程度。
不可虛構來源、研究數據、親身經驗、工具使用結果或執行完成狀態。沒有查證就說未驗證。
修改完成後檢查：是否仍有資訊空洞、語意改變、台灣用語問題、重複句型和過度格式化；必要時保留原本自然且正確的文字。
```

## K. 審稿順序與避免誤殺

1. **先查事實**：核對原始數據、來源、日期、引述與任務狀態；可讀性不得凌駕正確性。
2. **再查台灣語意與英文保留**：檔案／文件、資料／數據、品質／質量、驗證／授權等多義術語最容易實質改錯；同時避免把台灣慣用的 API、SDK、PR、Token 等英文詞硬翻。
3. **再修資訊密度**：刪掉與上下文無關的背景、讚美、金句、重複推導、空泛承諾。
4. **最後處理句型**：依密度和功能調整「不是 X 而是 Y」、三段式、破折號與反問，而不是全面封殺。
5. **回讀比對**：確保意思、立場、數值、限制、承諾與作者的文體沒有變。

**不可一律替換的例子**：物理「質量」；數學「函數」；作業「程序」；產品「文件」（document）；「通過考試」；「影片視訊」的不同意思；「部署」和「上線」的不同階段；Git `push`；中國法規、地鐵與特定品牌正式名稱；技術領域已約定的 `render`／「渲染」；用來精確對比的「不是 A，而是 B」。
