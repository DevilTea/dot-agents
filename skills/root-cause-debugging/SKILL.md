# 找根因

目標：找出有證據支撐的原因，並用一個在修正前失敗、修正後通過的檢查來證明。

## 步驟

1. **定義問題。** 寫下觀察到的行為、預期的行為，以及預期的依據（規格、契約、先前版本的行為）。說不出預期行為時，先釐清這一點，不要直接動手修。
2. **建立 baseline。** 可行時，用最小的步驟重現問題，並記下重現指令和結果。靜態證據已經足以證明問題，或重現的成本明顯不成比例時，可以不重現，但要寫明用了什麼證據、信心因此受到什麼限制。
3. **收集證據再提假設。** 讀錯誤訊息、log、相關程式碼和最近的變更（`git log`、`git diff`、`git bisect`）。列出能解釋**所有**觀察的假設，並依可能性排序。
4. **採用最簡單的解釋。** 優先檢查能解釋全部證據、需要最少額外機制的假設；不要為了說得通而追加沒有證據的機制。
5. **一次驗證一個假設。** 為每個假設設計一個會區分真假的檢查（加 log、縮小輸入、切換一個變數、回退一個 commit）。檢查結果不支持時，排除這個假設並記錄下來。
6. **確認因果。** 主張「某個修改造成了改善」時，要在同一個 baseline 上比較修改前後；歸因很重要時，做 ablation 或等效的對照（只拿掉這個修改，看問題是否回來）。一般修正只要有直接的正確性證據就夠，不需要每次都做 ablation。
7. **修正並加回歸檢查。** 寫一個在修正前失敗、修正後通過的測試或檢查。專案有測試時，把它加進測試套件。
8. **失敗時換方向。** 同一個做法重複失敗時，回到第 3 步換假設或換方法，不要原樣重試。沒有可行的做法時，回報阻礙和已經排除的假設。

## 回報內容

- 根因，以及支撐它的證據（重現指令、檢查結果）。
- 已經排除的假設，以及排除的依據。
- 修正內容，以及證明修正有效的檢查（修正前失敗、修正後通過）。
- 沒有驗證到的情境和剩下的風險。
